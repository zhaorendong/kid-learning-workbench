# 多端数据同步设计（v0.3）

> 面向的场景：iPad 上学的、电脑上学的、以后可能还有别的设备，
> 希望**同一份学习记录**而不是各记各的。
>
> 默认关闭。不开的时候整套东西不参与任何行为，站点仍然是纯本地零联网的。

---

## 1. 为什么不是"改数据库同步"

最直觉的做法是：每台设备把自己改过的记录推到服务器，服务器按字段合并。
这条路对**学习记录**来说很危险，因为冲突无处不在：

- iPad 和电脑同时给同一道错题打勾，谁赢？
- 一台把错题"移除"了，另一台把它"标为已订正"，合并后应该是什么？
- 时间戳相近的两次修改，靠 `updatedAt` 比大小，会静默丢掉一次操作。

所以这里不用"状态合并"，改用**事件日志 + 各端确定性重算**。

## 2. 核心机制：事件日志（event log）

```
本地操作（点勾 / 答题 / 改设置）
   ↓ ①本地立即改 DB 并渲染（界面不卡、离线可用）
   ↓ ②同时写一条事件进 outbox 队列
   ↓ ③推给服务器，服务器按到达顺序追加进日志并分配 rev
   ↓ ④各端把「服务器事件 + 本地未推送事件」按同一顺序重算一遍状态
```

关键点：**服务器不做任何业务合并**，它只做三件事——追加、按 id 去重、分配 rev。
于是所有设备最终拿到的事件序列（顺序 + 内容）完全一致，
归约（reduce）出来的状态必然一致，**多端自然收敛**。

事件长这样：

```js
{ id: 'dev-a1b2c3:17', t: 'answer', ts: 1757836800000, d: 'dev-a1b2c3',
  mid: 'math-calc', q: '3+5', answer: '8', my: '9', right: false }
```

- `id` = `设备id:自增序号` → 全局唯一，**重传幂等**（网络抖动/重复提交不会重复计数）
- `t` = 事件类型（`answer` / `done` / `progress` / `profile` / `settings` / `mistakes` / `checkpoint` …）
- `ts` = 设备本地时间（仅用于展示与兜底，**不参与排序**，避免设备时钟不准导致乱序）

### 冲突的真实表现（诚实说明）

同步不解决"同一秒两台设备改同一件事"，它只保证**最终一致且不丢操作**：
两个操作都会进日志、都会生效，顺序由服务器到达顺序决定。
对家庭学习场景（孩子在一台设备上学习）来说这已经足够。

## 3. 为什么 `rebuild()` 是安全的

`core.js` 里所有本地写入**本来就走同一套推导**（`progress / log / mistakes / achievements`
都由事件累加得出），所以"本地直接改 DB"和"用事件重算"结果一致。
`rebuild()` 只是把同样的推导换成"以服务器事件为准"再跑一遍：

- 快照类事件（导入备份 / 清空数据）在日志里表现为 `checkpoint`，
  之后的事件叠加在它上面 → **导入备份这个动作也能同步给其他设备**。
- 重算永不删本地未推送事件：它们还在 outbox 里，下一轮会补交。

## 4. 服务端

单文件 Python 标准库实现（`_build/server/server.py`），无第三方依赖，
跑在 部署机 上（Windows 计划任务 `XYBDataServer`，开机自启），监听 `0.0.0.0:8100`。

数据目录（部署机 本机）：

```
config.json     口令哈希（只存 sha256，不存明文）
events.jsonl    事件日志（一行一个事件，追加写）
meta.json       gen / rev / 设备列表
versions/       回滚快照（每次回滚/重置前自动留档）
server.log      运行日志
```

### 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/ping` | 存活探测，**不需要鉴权**，返回 `keySet`（是否已设口令） |
| POST | `/api/setkey` | 首次设置口令（已设过则拒绝，防止被改） |
| GET | `/api/info` | rev / gen / 事件条数 / 设备列表 |
| GET | `/api/events?since=&gen=` | 增量拉取（`gen` 不一致时强制全量） |
| POST | `/api/sync` | **主接口**：推本地事件 + 拉新事件，一次往返 |
| GET | `/api/versions` | 回滚快照列表 |
| POST | `/api/rollback` | 回滚到某个 rev（截断日志 + gen+1 触发全网重同步） |
| POST | `/api/reset` | 清空（需 `confirm: true`，同样留快照） |

### 鉴权：口令不上网明文传

前端把口令算成 `sha256('xyb::' + 口令)`，作为 `Authorization: Bearer <hash>`。
服务端只存这个哈希。**注意**：站点跑在 `http://` 下属于"非安全上下文"，
浏览器不提供 `crypto.subtle`，所以 `sync.js` 里自己实现了一份纯 JS sha256
——不是为了炫技，是环境逼的。

> 安全性如实交代：这是**家庭内网**方案，防的是"邻居扫到端口乱看"，
> 不是防有能力的攻击者（http 明文传输本身可被中间人看到哈希）。
> 不要在公网暴露 8100。

## 5. 客户端开关与首次接入

`assets/sync.js` 挂载 `window.XYBSync`，配置存在 `xyb.v1.cloud`：

```js
{ enabled:false, url, key, gen, rev, lastSyncAt, lastError, deviceId }
```

- **默认关闭**：`emit()` 直接 return，outbox 不增长，页面行为与 v0.2 完全一致。
- 只有在 `parent.html` 里"连接并开启"之后事件层才开始记录。

首次接入时要问一句**以哪边为准**（`connect()` 返回 `needChoice`：
服务端已有数据 **且** 本机已有学习记录）：

| 选择 | 行为 |
|---|---|
| 以云端为准 | 丢弃本机状态，全量拉取服务器事件重算 |
| 以本机为准 | 把本机当前状态打成一个 `checkpoint` 事件推上去，作为新基线 |

选完写 `activate(url, key, mode)`，之后 `flush()` 进入常规循环：
**改动后 2.5 秒防抖推送**、每 30 秒兜底轮询、切后台/关页面时立即推一次。

## 6. 断网与失败处理

| 情况 | 行为 |
|---|---|
| 服务器连不上 | 事件留在 outbox，界面照常用；`lastError` 显示在家长端 |
| 口令错/未设置 | 标记 `needKey`，家长端提示重新设置，不反复重试 |
| outbox 涨太大 | 超 2000 条截断、超 7 天的事件丢弃（服务端长期拒收的兜底） |
| 服务器 gen 变了 | 说明回滚/重置过 → 丢掉本地旧事件，全量重拉 |

## 7. 已知边界

1. **删除类操作不会传播"删除"语义**，而是通过 `checkpoint` 或具体事件表达
   （例如清空数据 = 一个 checkpoint），保证重算结果一致。
2. 每台设备的 `localStorage` 仍各自保存一份完整状态（离线可用是硬要求），
   同步只是让它们收敛到同一份。
3. 服务器是**单点**：部署机 关机/没登录时同步停摆，但学习功能不受影响。
4. 家长 PIN 与同步口令是两码事：前者只管界面门禁，后者是数据服务的凭证。
